## 2. 不成立的条目（建议删除或改写）

### 2.1 ❌ L5 —— "release 下无法跑测试"不成立（已实测）

**原文**：`panic = "abort"`（release）无配套措施，release 下无法跑测试。

**核实**：`panic = "abort"` 确实在 `Cargo.toml` 的 `[profile.release]` 且无注释；但 **cargo 对测试/基准目标
自动忽略 `panic` 设置**（测试需要 unwind）。最小复现（与项目同配置）：

```toml
[profile.release]
panic = "abort"
```

```text
$ cargo test --release
test result: ok. 1 passed; 0 failed
```

**结论**：删除"无法跑测试"的表述；该条可整体删除，或降级为一句注释建议
（"release abort 为体积取舍，建议补一行注释说明"）。

### 2.2 ❌ J9（子项）—— "喜欢失败乐观态不回滚"不成立

**原文**：J9 内"喜欢失败乐观态不回滚（`ui/playback.rs:377`）"。

**核实**：`toggle_like_song`（`ui/playback.rs:350-380`）在错误分支**已有回滚**：

```rust
Some(Err(err)) => {
    if like { this.liked.remove(&id); } else { this.liked.insert(id); }  // ← 回滚
    this.notifications.update(cx, |n, cx| n.error(err.user_message(), cx));
}
```

且该回滚在 `3aa0d5d`（"歌曲行内红心"提交，**早于**本清单提交 `400faa5`）即已存在——
清单写作时点就不成立。仅 `None => {}` 分支无回滚，但 oneshot 发送端必然发送，`None` 实际不可达。

**结论**：删除该子项。J9 其余 5 个子项（`remove_playlist` / `move_playlist` / 队列操作不落盘 /
空队列残留 / 扫码未知 code）均核实成立，保留。

### 2.3 ❌ M12 —— "slider 回环卡死拖动态"不成立（已核对组件源码）

**原文**（清单自标"待确认"）：进度条 `set_value` 若回环触发 `SliderEvent::Change`，
tick 每 16ms 的程序化更新会把进度条卡死在拖动态。

**核实**（`gpui-base-0.7.3/src/slider.rs`）：
- `SliderState::set_value`（程序化路径）**只改值 + 刷 thumb + `cx.notify()`，不发射任何事件**；
- `cx.emit(SliderEvent::Change(...))` 仅在**指针拖拽路径**（`slider.rs:391`）发射；
- Siren 侧 `seeking = true` 只订阅 `SliderEvent::Change`（`ui/playback.rs:175-180`）。

**结论**：不存在回环，tick 的程序化更新不会进入 `seeking` 态。可删除该条（或改写为
"已验证非问题"备注）。

## 3. 需升级的条目

### ⬆️ K9 —— 成立，且严重度被低估：这是**确定性 panic**（已实测）

**原文**：账号页三处网络请求跑在 UI 执行器（`signin` / `save_profile` / `change_avatar`），
"reqwest 在无 reactor 上下文行为不可靠"。

**核实链路**：

1. **GPUI 前台执行器 = 主线程，且无 tokio 上下文**：
   `gpui-pre` 全系（含 `gpui-pre-scheduler`）**零 tokio 依赖**（Cargo.toml 核实）；
   `Context::spawn` 注释 "on the main thread"，链路为
   `context.rs:230`（`Context::spawn`）→ `app.rs:2297`（`App::spawn`，
   "Spawns the future ... **on the main thread**"）→ `foreground_executor.spawn(...)`。
2. **Siren 从不进入 tokio 上下文**：全库无 `.enter()`，仅 `Runtime::new()`（`lib.rs:54`）并持有句柄。
3. **实测**（与项目同版本依赖）：在无上下文线程轮询 `reqwest` future：

   ```text
   thread 'main' panicked at tokio-1.53.2/src/net/tcp/stream.rs:164:
   there is no reactor running, must be called from the context of a Tokio 1.x runtime
   ```

   且**变体验证**：客户端先在 `rt.enter()` 内构建、再到外部轮询——**同样 panic**
   （socket 注册是"轮询线程局部"的，客户端构建位置无关）。
4. **对照**：`account.rs` 的 `load()`（读路径）正确使用 `handle.spawn + oneshot`；
   仅三个写路径违规——一旦用户点击（签到/保存资料/换头像）即 panic（或被任务层吞掉表现为"没反应"）。

**结论**：K9 从 **P1 升 P0**；标题改为"账号页三处网络请求在主线程轮询 → **必 panic**"；
修复方向（统一 oneshot + `handle.spawn`）不变。

## 7. 附：评审方法说明

- **静态核实**：对每一条目读取其引用的源码位置（或其等价位置——行号存在少量漂移），
  确认描述的机制在当前代码成立；对依赖行为（gpui 执行器、滑块事件、tokio IO）进一步阅读
  `~/.cargo/registry` 内对应 crate 源码。
- **动态验证**（2 项）：
  - `panic=abort` × `cargo test --release` —— 结论：正常通过（否定 L5）；
  - 无 tokio 上下文轮询 reqwest（含"客户端在上下文中构建"变体）—— 结论：确定性 panic（升级 K9）。
- **版本一致性**：实验用 `tokio 1.53.2` / `reqwest 0.12.28` 与项目 `Cargo.lock` 锁定版本一致；
  `gpui-pre 0.3.9` / `gpui-base 0.7.3` 为项目实际依赖版本。
