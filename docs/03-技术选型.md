## 2. UI 框架：gpui-kit 🟢

### 选型理由

**GPUI Kit** 是 Longbridge 出品的 Rust 桌面应用框架，构建于 [GPUI](https://github.com/zed-industries/zed)
（Zed 编辑器的 UI 框架）之上。

| 指标 | 数值 |
|---|---|
| GitHub Stars | **16,900** |
| Commits | 2,555 |
| 组件数 | 75+ |
| 生产验证 | **Longbridge Pro**（已上线的商业桌面应用） |

### 关键能力匹配

| Siren 需求 | gpui-kit 能力 |
|---|---|
| 歌单/曲目长列表 | **Virtual Lists**（支持不等高条目） |
| 播放队列表格 | **Data Tables**（虚拟滚动、可调列宽、排序，支持数十万行） |
| 侧栏 + 主区布局 | **Dock Layout**（可拖拽、可嵌套、可序列化） |
| 歌词滚动动画 | **120 FPS** GPU 加速 |
| 主题/取色 | 语义化主题系统、多尺寸支持 |
| 图标 | 内置 Lucide 图标集 |

### 架构分层

```
gpui-kit             应用唯一依赖
├── gpui-base        无样式行为/状态/基础设施
└── gpui-component   完整样式化 UI 系统（75+ 组件）
```

设计哲学对标 **shadcn/ui**：「行为归基础层，表现归应用层」。
可选择用完整组件系统，也可在 `gpui-base` 上自建设计系统。

### 跨平台支持

GPUI 的 feature 中已包含 `wayland` 与 `x11`，`windows-manifest`，
明确支持 macOS / Windows / Linux。

### 备选方案对比

| 框架 | 模式 | 优势 | 劣势 |
|---|---|---|---|
| **gpui-kit** | GPUI（保留模式，组件化） | 组件丰富、商业验证、性能强 | 生态较新 |
| `egui` | 立即模式 | 生态最成熟、上手快 | **复杂布局与动画能力弱**，不适合精细 UI |
| `iced` | Elm 架构（保留模式） | 心智模型接近 Compose | 组件较少，需自建较多 |
| `Qt`（Rust 绑定） | 传统 retained | 成熟 | 绑定维护差，体积大 |

> **注意**：Melodia 桌面端有大量精细 UI（逐字歌词动画、Vibrant 取色、卡片布局、
> 悬浮滚动条）。**立即模式 GUI（egui）做这些会很痛苦**，可能比 Compose 更费劲。
> gpui-kit 的保留模式 + GPU 渲染更适合本项目。

## 3. 系统托盘：tray-icon 🟢

| 指标 | 数值 |
|---|---|
| 维护者 | **Tauri 团队** |
| 版本 | 0.26.1 |
| 下载量 | **34,255,405** |

### 平台封装

| 平台 | 底层实现 |
|---|---|
| Windows | `Shell_NotifyIcon` |
| Linux | StatusNotifierItem（SNI over D-Bus） |
| macOS | `NSStatusItem` |

### ⚠️ 关键：Linux 必须显式启用 `ksni` feature

`tray-icon` 在 Linux 上有两套后端，**默认那套会把 GTK3 拖进来**：

| feature | 后端 | GTK 依赖 | 说明 |
|---|---|---|---|
| `libappindicator`（**默认**） | `libappindicator` + `muda/gtk3` | ❌ **需要 GTK3** | 不推荐 |
| **`ksni`** | `ksni`（纯 D-Bus） + `muda/snapshot` | ✅ **零 GTK** | **本项目采用** |

```toml
[dependencies]
tray-icon = { version = "0.26", default-features = false, features = ["ksni"] }
```

**收益**：

1. **去掉 GTK3 依赖** —— 打包时不必引入 GTK 全家桶
2. **菜单同样走 D-Bus** —— `muda/snapshot` 用 DBusMenu 协议，由宿主原生渲染
3. **Wayland 下本就正确** —— SNI 是 D-Bus 协议，与显示协议无关；
   选 `ksni` 从源头避开了 XEmbed 回退路径（该路径在 Wayland 下收不到鼠标事件）

> ⚠️ 忘记加 `default-features = false` 是最容易犯的错——
> 编译能过，但会静默引入 GTK3 依赖。

### 价值

Melodia **手写了 400+ 行** Linux 托盘代码（SNI + DBusMenu 实现），涵盖：

- SNI 协议对象导出
- DBusMenu 菜单布局
- 图标 PNG 编码
- 宿主坐标换算

`tray-icon` **可直接替代**这些工作。这是选择 Rust 生态的主要收益之一。

### 不引入 `TrayIntegration` trait

`tray-icon` 已提供三平台统一 API，**无需再抽象一层**。
仅当未来需要更换实现（如 crate 停更）时才考虑引入。

## 4. 目录规范：directories 🟢

| 指标 | 数值 |
|---|---|
| 版本 | 6.0.0 |
| 下载量 | **74,573,398** |

### 说明

`directories` 是 `directories-jvm` 的 **Rust 原版**。

> **重要**：Melodia 曾评估 `directories-jvm` 后**决定不用**，原因是它会在 Windows 上
> 多插一层 `data/` 目录，破坏已有用户的升级路径（旧数据在 `%APPDATA%\Melodia\`，
> 换库后会去 `%APPDATA%\Melodia\data\` 读）。
>
> **Siren 是全新项目，无历史包袱**，可直接采用，无需担心此问题。

### 输出示例

```rust
let dirs = ProjectDirs::from("com", "cyanrhythm", "Siren").unwrap();

// Windows:  %APPDATA%\Siren
// Linux:    ~/.config/siren
// macOS:    ~/Library/Application Support/com.cyanrhythm.Siren
dirs.config_dir();

// Windows:  %LOCALAPPDATA%\Siren\cache
// Linux:    ~/.cache/siren
// macOS:    ~/Library/Caches/com.cyanrhythm.Siren
dirs.cache_dir();
```

## 5. 系统媒体控制：playwire 🟡

| 指标 | 数值 | 判断 |
|---|---|---|
| 版本 | 2.0.0（2026-10 发布） | 较新 |
| 下载量 | **3,050** | ⚠️ 偏少 |
| 维护者 | 个人 | ⚠️ 单人 |
| 描述 | MPRIS / SMTC / Now Playing 统一 API | ✅ 定位准确 |

### 风险

**3 千下载量意味着实际场景验证不足。** 而系统媒体控制恰恰是坑最多的部分：

Melodia 在真实 KDE 环境踩到的 8 个坑（详见
[`02-平台能力规格.md § 3.4`](02-平台能力规格.md#34-linux-mpris-实现要点血泪经验)）：

1. 必须先导出对象再抢总线名（否则 KDE 永久忽略该播放器）
2. 必须实现 `MediaPlayer2` 根接口
3. 必须提供 `CanPause` / `CanStop`（KDE 读不到会短路）
4. `mpris:trackid` 必须是对象路径类型
5. `xesam:artist` 是字符串数组
6. `mpris:length` 是微秒
7. 需主动推送 `PropertiesChanged`
8. `Set` 要接受 `LoopStatus` / `Shuffle`

**这些坑一个冷门库很可能都没覆盖。**

### 建议

**策略 A（推荐）：先用 playwire 做 PoC**

验证周期约 1 周，在 KDE 与 GNOME 上逐条测试上述 8 点。若通过则采用。

**策略 B（备胎）：`zbus` + 自研 MPRIS**

| 指标 | 数值 |
|---|---|
| zbus 版本 | 5.19.0 |
| zbus 下载量 | **93,915,806** |
| 成熟度 | 🟢 极高 |

- 工作量约 **300–400 行**
- Melodia 已有 Kotlin 实现（`LinuxSystemMediaSession.kt`，371 行）**可逐行对照移植**
- **因已知全部坑点，自研反而可能比赌冷门 crate 更稳**

### Windows / macOS

| 平台 | 方案 |
|---|---|
| Windows | SMTC（WinRT）—— playwire 若不可用，需 `windows` crate 绑定 |
| macOS | `MPNowPlayingInfoCenter` —— 通过 `objc2` 或 `objc2-media-player` 绑定 |

## 6. 音频引擎：libmpv 绑定 🟡

### 为什么选 libmpv

继承 Melodia 的选型结论（该结论经过实践验证）：

| 需求 | 为何排除其他方案 |
|---|---|
| 播放网易云加密音频流 | 需 HTTP 流式拉取 + 边下边播 |
| **边播边录制缓存** ⭐ | 依赖 mpv 原生 `stream-record` —— 决定性需求 |
| **双引擎交叉淡入** | 需两台引擎做音量 ramp |
| 多音频设备选择 | mpv 的 `audio-device-list` |
| 宽格式兼容 | 底层 FFmpeg |

**关键排除理由**：
- `Java Sound` 只支持 WAV/AIFF，无 HTTP 流、无 seek 缓冲
- `JavaFX Media` 格式支持少、无流录制
- VLC 方案过重（每实例拖整个运行时），双实例开销大

### Rust 侧的绑定选择

crates.io 上的候选（均为小规模项目）：

| crate | 下载量 | 说明 |
|---|---|---|
| `mpv` | 27,020 | safe bindings，相对最成熟 |
| `tauri-plugin-mpv` | 6,669 | Tauri 专用 |
| `mpv-client-dyn` | 1,575 | 动态加载 |
| `mpv-client-cross` | 332 | 跨平台客户端 API |
| `mpv-engine` | 380 | 工具包无关的嵌入核心 |

**风险**：这些绑定都**规模很小**，可能需要：
1. 试用 `mpv` crate，验证 `stream-record` 等高级选项是否暴露
2. 若不满足，用 `mpv-client-cross-sys` + 自己的安全封装（Melodia 的 `LibMpv.kt` 只映射了 11 个 API，移植成本低）

> **利好**：Melodia 的 libmpv 集成只用了 **11 个 C API**（`LibMpv.kt`），
> 且有完整的 `MpvEnginePair`（交叉淡入）、`AudioCache`（流录制）实现可对照。
> 这意味着**即使从零写绑定，工作量也可控**。

### 结论（已定）

- `mpv` crate 已于 **2017 年停更**（依赖 `log 0.3` / `num 0.1`），**不采用**。
- 需运行时动态加载（libmpv 缺失时降级），而多数维护中的绑定都**构建期链接**，
  且 `mpv-client-dyn` 为 **GPL-3.0**（与 MIT 目标冲突）。
- **选型：手写 `libloading` 运行时绑定**（`crates/siren-core/src/player/mpv.rs`），
  逐一映射 11 个 API，满足优雅降级、许可干净、无 Windows 导入库问题。已真机验证出声。

## 7. 窗口特效：window-vibrancy 🟡

| 指标 | 数值 |
|---|---|
| 维护者 | Tauri 团队 |
| 版本 | 0.8.1 |
| 下载量 | **23,585,984** |
| 依赖 Tauri 运行时 | ❌ 无 |

### 能力

为窗口施加系统级半透明/模糊效果：

| 平台 | 效果 |
|---|---|
| Windows | Acrylic / Mica / Blur（Win10/11 各有差异） |
| macOS | `NSVisualEffectView`（毛玻璃） |
| Linux | 不支持（返回 `UnsupportedPlatform`） |

### 对 Siren 的价值

音乐播放器适合半透明侧栏或播放条（如 macOS 的毛玻璃质感）。

### ⚠️ 需验证的兼容性问题

**GPUI 自行管理窗口**，而 `window-vibrancy` 需要操作**原生窗口句柄**
（Windows `HWND` / macOS `NSWindow`）。

若 GPUI 未暴露原生句柄获取接口，则此 crate **无法接入**。

**验证方式**（见 [`05-PoC验证清单.md`](05-PoC验证清单.md)）：

1. 确认 GPUI 能否拿到当前窗口的原生句柄
2. 若可以，测试 `window-vibrancy` 是否生效
3. 检查是否与 GPUI 的渲染/重绘冲突

> **结论**：列为 **P2 可选增强**，不作为核心依赖。Linux 上本就不可用，
> 若验证不通过直接放弃，不影响主体功能。

## 10. Tauri 生态 crate 评估

> Tauri 团队在桌面开发上积累深厚，其 crate 质量普遍较高。
> 但需注意：**Tauri 的多数 crate 是"插件"，依赖 `tauri` 运行时**，
> 而 Siren 用 GPUI 作为 UI 框架，**不能引入 Tauri 运行时**（会带进 `tao` + `wry` + WebView）。

### 10.1 判定标准

| 类型 | 可用性 |
|---|---|
| 独立 crate（不依赖 `tauri`） | ✅ 可用 |
| `tauri-plugin-*`（依赖 `tauri`） | ❌ 不可用 |
| `tao`（窗口管理库） | ❌ 与 GPUI 的窗口管理冲突 |

### 10.2 ✅ 可独立使用

| crate | 下载量 | 用途 | Siren 决策 |
|---|---|---|---|
| `tray-icon` | 34,255,405 | 系统托盘 | ✅ **已采用** |
| `window-vibrancy` | 23,585,984 | 窗口毛玻璃/亚克力 | 🟡 可选增强（见 § 7） |
| `auto-launch` | 6,653,729 | 开机自启 | ✅ **已采用** |
| `global-hotkey` | 6,178,929 | 全局快捷键 | ✅ **已采用** |
| `tauri-winrt-notification` | 10,306,503 | Windows 原生 Toast | 🟡 仅 Windows，见 § 10.4 |

> 注：`tao`（窗口管理）虽不依赖 `tauri`，但它与 GPUI **功能重叠**，
> 两者都会创建/管理原生窗口，同时使用会冲突，因此**不采用**。

### 10.3 ❌ 不可用（依赖 Tauri 运行时）及其替代方案

以下是看起来有用、但因绑定 Tauri 运行时而**不可用**的插件，以及对应替代方案：

| Tauri 插件 | 用途 | 替代方案 |
|---|---|---|
| `tauri-plugin-single-instance` | 单实例运行 | 自实现（文件锁 / 本地端口，约 50 行） |
| `tauri-plugin-window-state` | 保存窗口位置尺寸 | 自实现（序列化 JSON，约 40 行） |
| `tauri-plugin-positioner` | 窗口定位 | 自算屏幕坐标 |
| `tauri-plugin-clipboard-manager` | 剪贴板 | [`arboard`](https://crates.io/crates/arboard) |
| `tauri-plugin-opener` | 打开文件/URL | [`opener`](https://crates.io/crates/opener) |
| `tauri-plugin-notification` | 系统通知 | [`notify-rust`](https://crates.io/crates/notify-rust) |
| `tauri-plugin-store` | 键值存储 | `serde` + 文件 |
| `tauri-plugin-updater` | 应用内更新 | 自建（检查版本 + 下载，逻辑简单） |
| `tauri-plugin-autostart` | 开机自启 | **用底层 `auto-launch`** ✅ |
| `tauri-plugin-global-shortcut` | 全局快捷键 | **用底层 `global-hotkey`** ✅ |
| `tauri-plugin-os` | 系统信息 | `std::env::consts::OS` |
| `tauri-plugin-log` | 日志 | [`tracing`](https://crates.io/crates/tracing) + `tracing-subscriber` |
| `tauri-plugin-dialog` | 原生文件对话框 | [`rfd`](https://crates.io/crates/rfd) |

> **重要观察**：`tauri-plugin-autostart` 与 `tauri-plugin-global-shortcut`
> 分别只是 `auto-launch`、`global-hotkey` 的 Tauri 封装 ——
> **直接用底层 crate 即可**，无需 Tauri 这层。

### 10.4 关于通知

| 平台 | 方案 |
|---|---|
| Windows | `tauri-winrt-notification`（WinRT Toast）<br/>⚠️ 官方描述为 "An incomplete wrapper" |
| Linux | [`notify-rust`](https://crates.io/crates/notify-rust)（走 `org.freedesktop.Notifications`） |
| macOS | `notify-rust` 或 `objc2` 绑 `UNUserNotificationCenter` |

**建议**：在 `siren-platform` 中定义统一的 `Notification` trait，
三平台分别实现（详见 [`02-平台能力规格.md`](02-平台能力规格.md)）。

```mermaid
    B --> B1["tauri-plugin-* × 44"]

    B1 --> C["替代：底层 crate 或自实现"]

    A1 --> R["采用"]
    C --> R

    style A fill:#14532d,stroke:#86efac,color:#fff
    style A1 fill:#14532d,stroke:#86efac,color:#fff
    style R fill:#1e3a5f,stroke:#93c5fd,color:#fff
    style B fill:#7f1d1d,stroke:#fca5a5,color:#fff
    style B1 fill:#7f1d1d,stroke:#fca5a5,color:#fff
```

**两条原则**：

1. **用 Tauri 的独立 crate，不用 Tauri 本身** ——
   引入 Tauri 运行时会带进 `tao`（窗口）+ `wry`（WebView）+ 整个生态，
   与 GPUI 严重冲突。
2. **插件不可用时，优先找底层 crate** ——
   多数 `tauri-plugin-*` 只是对底层库的封装，直接用底层即可。
