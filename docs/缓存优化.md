# 图片缓存优化

> 审查日期：2026-10-16 · 基线：`cd39246`（工作区干净）
> 对照对象：Melodia（`/home/cyan/code/source/software/Melodia`，Compose Multiplatform 桌面，Coil 3）
> 范围：封面/头像的加载、缓存与尺寸策略（不含音频缓存）
> 结论：**Siren 的缓存没有任何上限**，且"预取档位"与"渲染尺寸"是两套独立硬编码——
> 这是内存单调增长与"永久占位"风险的共同根因。修复方向不是换缓存库，而是补上
> 「上限 + 淘汰 + 可观测 + 可清除」，并把尺寸收敛为单一真源。
> 另：对照发现 Melodia 对 hero 级表面（全屏播放封面/取色）走**原图 + 本地缩放**，
> 而 Siren 的 512 档封顶在 2× 屏大窗下偏糊，见 3.2 与 P2.6。

## 1. 现状：三张表 + 两层常驻，全部无上限

`CoverLoader`（`crates/siren-app/src/ui/covers.rs:29-36`）是唯一入口，内部三张 `Arc<Mutex<..>>` 共享表：

| 表 | 键 | 值 | 写入 | 删除 / 淘汰 |
| --- | --- | --- | --- | --- |
| `cache` | 档位化 URL（含 `?param=WyH`） | `Arc<Image>`（压缩字节） | `covers.rs:125` | **无**（全文件无 `remove`/`clear`/`retain`/`evict`） |
| `colors` | 去 query 的 base URL | `Rgba` | `covers.rs:122` | **无**（每条约 100 B，量级可忽略） |
| `inflight` | 档位化 URL | — | `covers.rs:99` / 删 `:129` | 抓完即删，自限 |

**第二层常驻（框架侧）**：`img(Arc<Image>)` → `ImageSource::Image`（gpui-pre `elements/img.rs:113-117`）
→ `window.use_asset::<ImageDecoder>`（`img.rs:550`）→ `App::asset_entry`：

```rust
let asset_id = (TypeId::of::<A>(), hash(source));   // hash(Image) = image.id（内容哈希）
if !self.loading_assets.contains_key(&asset_id) { /* 插入后不再移除 */ }
```

（gpui-pre `app.rs:3010-3042`）。项目从不调用 `remove_asset`（全仓 grep 0 命中），
因此**解码后的 BGRA 帧同样常驻**。即：一张封面在内存里有两份——压缩字节（App）+ 解码位图（框架）。

### 1.1 单张成本与增长量级

解码是精确的 `W×H×4`；压缩按网易 CDN 的 JPEG 量级估计：

| 档位 | 压缩（估） | 解码 BGRA | 主要触发点 |
| --- | --- | --- | --- |
| 64 | 2–4 KB | 16 KB | 列表行 40/48、播放条 56、队列 40、头像 24/32 |
| 128 | 6–10 KB | 64 KB | 专辑 hero 120、个人主页头像 108、每日推荐 72 |
| 256 | 20–30 KB | 256 KB | 歌单 hero 200、首页货架 168 |
| **512** | 60–100 KB | **1 MB** | **每切一首歌**（`ui/mod.rs:662-663`） |

一场两小时会话的估算：听 100 首 ≈ 100×(1 MB + 80 KB) = **110 MB**；
浏览 2000 张列表封面 ≈ 2000×19 KB = **38 MB**；合计约 **150 MB 且单调增长**
（`CoverLoader` 挂在 `Services` 上，活到进程退出；框架 `loading_assets` 同理）。
重复播放同一首不重复计数（`covers.rs:96` 命中即跳过）。

## 2. 尺寸机制：档位是键的一部分

```rust
image(url, size):
  ① bucket(size)             // [64,128,256,512] 中第一个 ≥ size，向上取整
  ② sized_url(url, bucket)   // 126.net 且无 param= 时追加 "?param=WyH"
  ③ cache.lock().get(&key)   // 唯一一次查表；未命中 → 占位，不抓取
```

- **渲染尺寸可以任意**（`img().w(px(size))` 会缩放），但**预取与渲染必须同档**；
  档位不同 → 键不同 → `image()` 永不命中 → **永久占位**（渲染路径不发起网络，`covers.rs:5`）。
- 实测成本（本机 200 万次）：`bucket` 2.4 ns + 拼键 302 ns + 查表 52 ns；
  其中 84% 是每帧重建键字符串，不是哈希。
- 当前 45 处 `prefetch` 与 35 处渲染调用**逐条核对后档位一致**，唯一例外见 2.2。

### 2.1 键的边界情况

1. **URL 自带 `param=` 或非 `126.net`** → `sized_url` 原样返回 → 四个档位塌缩成同一个键：
   24px 头像与 512 封面共用一张原图（浪费带宽），首次抓取的尺寸决定全局画质。
2. **子串匹配**：`url.contains("126.net")` 也会命中 `1126.net` 之类的域名。
3. **无淘汰**：同一 URL 最多常驻 4 份压缩字节 + 框架侧 4 份解码位图。

### 2.2 唯一的档位错配风险：正在播放栏大封面

```
预取：prefetch([cover], 512.0)                     ui/mod.rs:663（切歌时）
渲染：cover_size = (np_effective_w - 28).clamp(220, 420)   now_playing.rs:60-62
```

两者**尺寸不等、只有档位相等**（需要 `cover_size ≥ 257`，即 `np_effective_w ≥ 285`）。
`np_effective_w = min(setting, vw-732).max(44)`，正常窗口下 ≥ 308 成立；
但窗口被压到声明的最小宽以下时（Wayland 合成器可忽略 `window_min_size`、`SIREN_W` 强制小窗）
会掉到 284 以下 → 256 档 → **封面永远灰色占位，切歌也不恢复**。

## 3. 参考实现：Melodia 桌面（Coil 3）

Melodia 不自建图片缓存，全部交给 Coil 3，**两层都有硬上限**（`desktopApp/.../data/DesktopImageLoader.kt`）：

```kotlin
private const val MEMORY_CACHE_PERCENT = 0.15        // :17  内存的 15%
const val DISK_CACHE_MAX_BYTES = 500L * 1024 * 1024  // :25  磁盘 500 MB
private const val DECODER_PARALLELISM = 4            // :19
private const val FETCHER_PARALLELISM = 8            // :20

ImageLoader.Builder(context)
    .memoryCache { MemoryCache.Builder().maxSizePercent(context, 0.15).build() }      // :37 LRU
    .diskCache  { DiskCache.Builder().directory(DesktopPaths.imageCacheDir.toOkioPath())
                                     .maxSizeBytes(maxBytes).build() }               // :38
    .decoderCoroutineContext(Dispatchers.IO.limitedParallelism(4))
    .fetcherCoroutineContext(Dispatchers.IO.limitedParallelism(8))
```

配套的工程细节（都是 Siren 缺的一圈）：

| 机制 | 位置 | 作用 |
| --- | --- | --- |
| `diskCacheSize()` / `clear()` | `:42-48` | 设置页「图片缓存 XX MB / 500 MB」+ 一键清除（`SettingsPage.kt:229-230`） |
| 磁盘位置走 XDG / `%LOCALAPPDATA%` | `DesktopPaths.localCacheDir` | 缓存与用户数据分离 |
| 启动后台删旧缓存目录 | `deleteLegacyCache()` `:51` | 老版本缓存在 `java.io.tmpdir`，daemon 线程清理 |
| 预热 `DiskLruCache` | Android `Thread { imageLoader.diskCache }.start()` | 避免首图加载的初始化锁竞争 |
| `crossfade(true)` | `MelodiaApplication.kt:75` | 淡入，避免硬切 |

### 3.1 尺寸策略：不分桶，但把"请求尺寸"与"显示尺寸"解耦

统一组件 `Cover`（`desktopApp/.../ui/components/Cover.kt`）：

```kotlin
fun sizedCoverUrl(url: String?, px: Int) =                     // :23
    if (url.contains("?")) url else "$url?param=${px}y$px"

@Composable
fun Cover(url: String?, size: Dp, requestSize: Dp = size) {    // :30-36
    val model = sizedCoverUrl(url, (requestSize.value * 2).toInt())  // :39 ← 乘 2（DPR）
    SubcomposeAsyncImage(model, contentScale = ContentScale.Crop,     // :44 ← 裁剪
                         error = { CoverFallback(size) })             // :46
```

`:35` 的注释是踩坑记录：

> 显示尺寸随拖动连续变化时传固定的请求尺寸，否则每帧换一个缩略图地址会不停重新加载

这正是 Siren 用 `bucket()` 想解决的问题。Melodia 的解法是"调用方传稳定的 `requestSize`，
显示尺寸随便变"，条目数靠 LRU 封顶。其余调用点（Android）为硬编码 80/100/120/150/200/250/300/400/500。
取色走独立请求：`substringBefore("?param=")` 归一化 + `size(640,640)` + `allowHardware(false)`
（`ColorExtraction.kt:47-57`），结果存 `LruCache<String, Palette>(150)`（`:224`）。

音频缓存同样自研淘汰（`AudioCache.kt:70-75`：按 `lastModified` 从旧到新删到 `maxBytes` 以内，
删不掉的跳过）——**"每个缓存都有上限"是 Melodia 的一致哲学**。

### 3.2 例外：hero 级表面走原图（"取大图、本地缩放"只此一处）

上面的缩略图路线有一个明确例外：**全屏播放页封面**。`FullPlayerScreen.kt:327-338` 主动把
`?param=300y300` 从 artwork URL 上**删掉**，拿到不带参数的原始 URL：

```kotlin
val rawCoverUrl = currentTrack.mediaMetadata.artworkUri?.toString()
    ?.replace("?param=300y300", "").orEmpty()                       // :328 ← 故意要原图
val previousCoverUrl = rememberQueueItemCoverUrl(...)
    .replace("?param=300y300", "")                                   // :335/338 ← 左右预览同样用原图
```

渲染链路一路不带尺寸：

```
SwipeToSkipCover → SwipeCoverLayer → AntiFlickerCoverImage          (SkeletonLoading.kt:94-144)
    AsyncImage(model = ImageRequest.Builder(context).data(url)
        .allowHardware(false).build())      // ← 没有 .size()：按原图分辨率下载 + 解码
```

所以这一处确实是"请求一张大图、按本地需求渲染"，且理由充分：封面尺寸大（竖排与宽屏两栏共用）、
要支持左右滑动切歌（同一 URL 同时挂当前/上一首/下一首三层）、还要取 bitmap 做透明封面检测与
描边阴影（`allowHardware(false)` 就是为此）。

**顺带澄清一个易混点：Coil 的 `.size()` 不改写网络 URL，只约束解码。** 取色路径正是如此——

```kotlin
val canonicalUrl = url.substringBefore("?param=")             // ColorExtraction.kt:51 / CoverPalette.kt:44
ImageRequest.Builder(context).data(canonicalUrl)
    .size(DECODE_MAX_DIMENSION, DECODE_MAX_DIMENSION)          // = 640，仅解码上限
```

即：**取色那次网络请求拉的也是原图**，只是解码到 640。这也解释了 Melodia 为何在 URL 上手写
`?param=`（真正控制下载量的是 URL，不是请求的 size）。

于是 Melodia 实际是**两级策略**：

| 表面 | 请求 | 复用方式 |
| --- | --- | --- |
| 列表/网格/头像/侧栏等日常面 | `?param=` 缩略图（桌面 = 显示尺寸×2） | 内存 LRU + 500 MB 磁盘 LRU |
| hero 面（全屏播放封面 + 取色 + 左右预览） | **原图**（一次），本地缩放到组件边界 | 同一张原图被三层滑动共享，靠缓存兜住一次性大下载 |

对 Siren 的直接推论：**hero 级表面不该被 512 档封顶**。NP 大封面在 420 逻辑 px、2× DPI 下
需要 840 物理 px，用 512 档渲染 ≈ 1.6× 拉伸（偏糊）；两条可选路线：

1. 给 hero 单独一档（如 1024），保持"尺寸可预测 + 带宽可控"；
2. 学 Melodia 走"原图 + 本地缩放"——**前提是先有磁盘缓存**，否则每次冷启动都要重下原图。

## 4. 对照表

| 维度 | Siren（GPUI 自建） | Melodia 桌面（Coil 3） |
| --- | --- | --- |
| 内存缓存 | `HashMap`，只 insert，**无淘汰** | `MemoryCache` = 内存 15%，LRU 按字节 |
| 磁盘缓存 | 无 | 500 MB LRU（XDG cache），可清除 |
| 缓存键 | 档位化 URL（4 档） | Coil 请求键（data + size + 变换） |
| 尺寸来源 | `bucket(size)` 计算，档位即请求尺寸 | `requestSize × 2`（吃 DPR）+ 约 10 处硬编码 |
| 尺寸变化的防抖 | 分桶天然收敛 | `requestSize` 与显示尺寸分离（`:35` 注释） |
| hero 表面（大封面/取色） | 仍走档位，**封顶 512**（2× 屏上 420 逻辑px 需 840，偏糊） | **原图 + 本地缩放**（`FullPlayerScreen.kt:328`），取色另发 640 解码上限的请求 |
| DPR | ❌ 请求尺寸 = 逻辑像素（2× 屏上 64 档铺 80 物理px，略糊） | ✅ 显式 ×2 |
| 缩放语义 | gpui `img()` 默认 `ObjectFit::Contain`（非方图留边） | `ContentScale.Crop`（裁剪） |
| 主色缓存 | `HashMap` 无上限 | `LruCache(150)` |
| 清除入口 / 用量显示 | 无 | 设置页「XX MB / 500 MB」+ 清除 |
| 常驻内容 | 压缩字节 + 框架解码 BGRA，两层都常驻 | 仅 LRU 内的解码 bitmap |

> 注：gpui `Img` 默认 `ObjectFit::Contain`（`img.rs:140`），即等比缩放"装进"盒子而非拉伸；
> 非方图会在盒内留边。网易封面是方图，故当前无可见问题，但语义应与产品预期（裁剪）对齐。

## 5. 优化方案

### P0 —— 消除"永久占位"与最猛的常驻（改动小、收益大）

- [x] **P0.1 预取档位从渲染尺寸推导，二选一收敛为单一真源**
  新增 `fn np_cover_px(np_w: f32) -> f32`（放 `now_playing.rs` 或 `theme.rs`），
  `now_playing.rs:60` 与 `ui/mod.rs:663` 都调它；`Root` 在 render 里记录 `last_np_w`
  （首帧未知时先预取 256）。彻底消除"512 vs 220–420"的隐式耦合。
  **落地**：未新增 `np_cover_px` 函数，改为 `NowPlayingUi.cover_px: Cell<f32>` 在渲染时写入，
  切歌预取直接读它（渲染与预取同源）。
- [x] **P0.2 降低 512 档的使用面**：`512` 只在 `np_cover_px ≥ 257` 时预取，否则 `256`
  （每首常驻 1.1 MB → 0.3 MB）；同时把 `cover_size` 的下限与预取档对齐。
  **落地**：更进一步——右栏**折叠时不预取大封面**（折叠态只渲染 44px 竖条），
  展开时对当前曲补一次；尺寸取渲染记录值，不再按阈值猜测。
- [~] **P0.3 `image()` 未命中时登记需求，允许自愈**：按 `(key)` 去重后投递一次 `prefetch`，
  完成后 `notify`。渲染路径仍只读，但档位不一致时表现为"晚一帧"，而不是永久占位。
  **2026-10-17 改方案**：未采纳（会在 render 里发起抓取，违反 `covers.rs` 自己的只读约定），
  改为 `lookup()` 的**只读档位回退**：精确档未命中时按 1024→64 查其它档，纯读、零副作用。
- [~] **P0.4 补一条回归测试**：把各 surface 的 `(prefetch 尺寸, render 尺寸)` 对照表写成
  断言（`bucket(prefetch) == bucket(render)`），防止后续新增页面再次踩错档位。
  **落地**：写了 `bucket` / `request_bucket`（DPR）/ `fallback_buckets` / `entry_cost` 与
  队列预取顺序的单测；逐 surface 对照表因尺寸依赖 viewport（如 NP 封面）未做，
  改由 `lookup()` 的只读回退兜底。

### P1 —— 缓存治理（上限 + 可观测 + 可清除）

- [x] **P1.1 `cache` 加字节上限 LRU**：按 `bucket² × 4 + 压缩长度` 估算单条成本，
  默认上限建议 64 MB（可写进设置）。**必须带 pin 集合**（当前曲 + 当前页面可见键），
  否则会淘汰掉屏上正在用的图，表现为"图突然变回占位"。
- [x] **P1.2 淘汰时同步释放框架侧解码副本**：`ImageSource::Image(arc).remove_asset(cx)`
  （`img.rs`，公开 API）→ `App::remove_asset::<AssetLogger<ImageDecoder>>`（`app.rs:3010`）。
  注意框架侧键是**内容哈希**（`hash(Image) = image.id`），两个 URL 指向同一内容时共享一条，
  因此仅当没有其它条目引用同一 `image.id` 时才调用。
- [x] **P1.3 `colors` 表随图片条目一起淘汰**（同源同生命周期）。
- [x] **P1.4 加 `stats() -> (条目数, 估算字节)`**：设置页显示 + 每 60 s 打一行日志。
  先有数字，再决定 LRU 上限。
- [x] **P1.5 设置页新增「图片缓存」节**：显示占用与上限 + 「清除图片缓存」
  （清除 = `cache.clear()` + 对每个 `image.id` 调 `remove_asset` + `colors.clear()`）。

### P2 —— 质量与带宽（可选，需实测）

- [x] **P2.1 请求尺寸乘 DPR**：`bucket(size * scale_factor)`；`scale_factor` 在 render 可得，
  由 `Root::render` 写入 loader（`set_dpr`），使 `prefetch`/`image` 共用同一 `key_for()`。
  代价：2× 屏上 40px 行从 64 档升到 128 档（带宽约 ×2）；如在意，可只对 ≥128 的显示尺寸乘 DPR。
- [x] **P2.2 显式 `.object_fit(ObjectFit::Cover)`**，与 Melodia 的 `Crop` 语义对齐。
- [x] **P2.3 磁盘缓存**：路径走 `directories`（XDG / `%LOCALAPPDATA%`），
  500 MB 上限 + LRU 淘汰 + 启动后台清理旧目录（对齐 Melodia `DesktopImageLoader`）。
  引入前需明确失效策略与隐私边界（封面 URL 含 `param`，可作为天然的档位键）。
  **落地（2026-10-18）**：`ui/cover_disk.rs`（`DiskCache`）+ `siren-platform::app_paths`
  的 `image_cache_dir()`（`<cache_dir>/image_cache`，Windows = `%LOCALAPPDATA%\cyanrhythm\Siren\cache\image_cache`）。
  键 = 档位化 URL（天然分档），文件名取其 **FNV-1a 128 位哈希**——缓存目录里看不到原始 URL；
  写入「临时文件 + rename」防半个文件；读取 touch mtime，超 500 MB 按 mtime 旧→新删到 450 MB；
  启动与每 60 s 在 blocking 池里 trim 并刷新用量（`stats()` 只读原子量，渲染路径不遍历目录）。
  失效策略：网易封面 URL 即内容地址，不做 TTL。`CoverLoader::prefetch` 先查磁盘、未命中才联网，
  网络成功后回写；设置页显示「磁盘 N 个文件 · X MB / 500 MB」，清除按钮同时清内存与磁盘。
  7 条单测覆盖：键→路径稳定性/文件名不含 URL、put/get 往返、trim 水位与最旧优先、
  清理残留临时文件、`clear` 保留目录、统计忽略临时文件、哈希稳定值。
- [x] **P2.4 取色改为独立档位、单一来源**：`dominant_color` 现在对**每个被抓取的档位**各解一次
  （`covers.rs:114-122`），且按 base URL 覆盖写入 → 同一首歌的调色板取决于"哪个档位最后到"
  （64 档小图与 512 档大图算出的主色可能不同）。改为固定档（如 128 或对齐 Melodia 的 640 上限）
  单独请求一次，或只在"最大档"完成时写入。
- [x] **P2.5 切歌预取去抖**：连续快速切歌时延迟约 300 ms 再预取，避免为路过曲目留下 512 档垃圾。
  **落地（2026-10-18）**：`Root::on_playback` 里播放条小图（56px）仍立即取（切歌瞬间要显示），
  **大封面改为 300ms 后仍停在该曲才取**（`cx.spawn` + timer，醒来读 `Playback` 当前曲比对，

**偏离之一：队列预取没有做成「窗口化」。**
队列面板对**全部行**渲染且 `smooth_scroll` 没有暴露滚动回调；只预取窗口会让远处行
永久停在占位（正是 P0 要消除的现象）。改为：当前曲优先排序 + 独立低并发额度
（批量 2 / 交互 6），总请求量不变，但不再一次打满连接，也不会让长队列把页面封面的
连接全占住（tokio 信号量 FIFO，共用一把会饿死交互预取）。

**未验证：Windows RSS。** `process_rss_bytes` 的 Windows 分支（`GetProcessMemoryInfo`）
本机（Linux）无法编译验证，依赖 `windows-latest` 的 CI 矩阵；macOS 返回 `None`。

## 8. 附：音频 / 元数据 / 歌词缓存（本文范围之外，2026-10-18 落地）

本文只覆盖图片。音频缓存另起一层，复用同一套磁盘 LRU：

| 项 | 做法 |
| --- | --- |
| 通用层 | `crates/siren-app/src/disk_lru.rs`：目录 + 字节上限 + mtime LRU + `tmp+rename` + 60s 后台 trim；图片与音频各一个实例 |
| 位置 | `cache_dir/audio_cache/`（`siren-platform::app_paths::audio_cache_dir`） |
| 键 | `{歌曲 id}-{音质档}.audio` —— 带档位，避免同一首不同音质互相覆盖 |
| 上限 | 2 GB（水位 1.8 GB） |
| 流程 | 播放前先查缓存：命中直接 `loadfile <本地路径>`（**连播放地址都不解析，断网可放**）；未命中照常流式播放，并在后台把同一份字节落盘（不阻塞起播） |
| 开关 | 设置页「音频缓存」：开关（默认开）、用量、清除；关闭后只流式播放、不落盘 |
| 实测 | 首次播放写入 `27946894-exhigh.audio`（6.2 MB）；重启后重播同一首日志为 `音频缓存命中` 且无「播放地址解析成功」 |

同一套 `DiskLru` 还带另外两层：

| 层 | 位置 / 上限 | 语义 |
| --- | --- | --- |
| 元数据 | `meta_cache/`，64 MB | 歌单/专辑/歌手详情 JSON：在线成功即写，**加载失败才读**；键为实体 id（id 本身账号唯一），`components/offline_hint.rs` 提示「离线缓存 · 可能不是最新」 |
| 歌词 | `lyrics_cache/`，75 MB | 解析后的 `LyricLine`：TTL 7 天、空结果 12h 负缓存；新鲜度存条目内（`fetched_at`），mtime 仅用于 LRU |

三层都在设置页各有「用量 / 上限 / 清除」，`DiskLru` 提供统一的 `tmp+rename` 写入、mtime LRU 与 60s 后台 trim。
